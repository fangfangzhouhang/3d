# 开发环境与依赖说明：把“能运行”变成可复现的共同起点

## 先给结论

当前项目最合适的团队基线不是“装满 YOLO、CUDA、3D 的 AI 环境”，而是：

```text
Windows 64 位 + CPython 3.12.x + venv + Python 标准库
```

这是因为当前 Mock 与软件回放框架只使用 Python 标准库；团队统一推荐 **CPython 3.12.x**，它对 OpenCV 等视觉依赖更稳妥。当前标准库测试也在本机 3.13 上通过，但新成员不必追求最新解释器。

这不是在回避视觉或控制，而是在避免让“安装过很多包”冒充“硬件系统已经准备好”。依赖应当跟着一张已批准的任务卡进入，而不是跟着技术名词提前进入。

## 审计结果：源文件到底说了什么

| 证据来源 | 发现 | 结论 |
|---|---|---|
| 当前 `microcleaning/`、`main.py`、`test/mcl/` | 只导入 `dataclasses`、`json`、`hashlib`、`pathlib`、`unittest` 等标准库 | 当前 Mock MCL **没有第三方 Python 依赖**。 |
| 当前仓库根目录 | 之前没有 `requirements.txt`、`pyproject.toml`、`environment.yml` 或 lockfile | 环境说明缺失，已由本文件和 `requirements/` 补齐。 |
| 历史提交 `b1abf5a` 的旧 `requirements.txt` | 曾列出 OpenCV、NumPy、Ultralytics、PySerial、Torch、YOLO 相关包等 | 那是旧原型的“功能愿望混合清单”，不是当前可复现环境，也没有证明这些包或功能曾在本项目成功联调。 |
| 当前测试 | Mock 契约测试 16/16 通过 | 仅证明软件流程与安全拒绝路径；不证明相机、串口、清洗或模型有效。 |

### 历史清单为什么不能直接恢复

旧清单把四类不同风险的东西放进同一个命令：图像采集、硬件串口、深度学习训练和系统工具。这样做的坏处是：一个同学只想修日志，也得背上 GPU / PyTorch 的安装风险；更糟的是，YOLO 能 import 并不等于它会识别你们的污染。

尤其不要因为历史文件写了 `torch`、`ultralytics`、`torchvision`、`torchaudio` 就默认安装它们。当前 P1 只验证固定顶视图 + OpenCV 基线；YOLO 需要等到这个基线出现可重复失败，并完成预登记 A/B 计划后才有资格进入。

## 三层环境：每层只为一个已知任务服务

| 环境层 | 谁使用 / 何时启用 | 依赖文件 | 能证明什么 | 绝不能证明什么 |
|---|---|---|---|---|
| 0：标准库框架 | 全员；今天即可使用 | `requirements.txt` | Mock 与软件回放框架可回归 | 真实图像或硬件效果 |
| 1：图像与 OpenCV | A/B 开始真实图片任务后 | `requirements/perception-opencv.txt` | 可做图像质量、分割与配准实验 | 检测已泛化或允许喷射 |
| 2：串口接口 | C 获得 STM32 协议后 | `requirements/control-serial.txt` | 可开发受限适配器和 ACK/超时测试 | 可直接驱动物理装置 |

模型训练、YOLO、CUDA、3D 重建不属于上述环境。它们未来应放在**单独的训练环境或远端 GPU 环境**，不应与控制真实泵、喷头的电脑耦合。控制端追求少依赖、可启动、可审计；训练端才追求算力。这是机器人系统里“把实验大脑和执行神经分开”的基本工程纪律。

## 新成员从零创建当前环境

在 `D:\大创\3d\MicroCleaningVision` 中运行：

```powershell
# 1. 建立项目专属环境；不要向系统 Python 全局安装项目包。
python -m venv .venv

# 2. 始终用这个解释器安装和运行。
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

# 3. 检查解释器和当前任务层；它不会安装包或访问硬件。
.\.venv\Scripts\python.exe scripts\check_environment.py --profile mock

# 4. 验证当前安全 Mock，而不是尝试启动硬件。
.\.venv\Scripts\python.exe -m unittest discover -s test\mcl -p "test_*.py" -v
.\.venv\Scripts\python.exe main.py
```

预期结果是 16 个测试通过，且控制台明确提示“本次没有访问任何真实硬件”。`output/` 中产生的是模拟回合记录，不能作为清洗实验结果上传或引用。

## A、B、C 分别何时加什么

### A：开始顶视图采集前

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements\perception-opencv.txt
.\.venv\Scripts\python.exe scripts\check_environment.py --profile perception
```

安装后首先验证的不是“能否运行 YOLO”，而是：相机是否能被系统识别、十张固定条件图像是否可保存、曝光/照明/聚焦是否有记录。若相机不是 UVC/DirectShow 兼容设备，而是厂商专用工业相机，**先记录精确型号与驱动/SDK 版本**，再由 A 提出一个最小适配器；不要盲装厂商 SDK。

### B：开始串口协议与伪控制器测试前

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements\control-serial.txt
.\.venv\Scripts\python.exe scripts\check_environment.py --profile control
```

这一步的验收是伪串口测试：`DENY`/`HUMAN` 不发字节，`ALLOW` 只发结构化有界命令，超时返回回执并请求安全停止。没有固件帧格式、ACK 语义、急停和联锁事实时，`pyserial` 只能用于模拟，不能连接真实端口。

### C：不需要安装“机械依赖”

C 的首要产物是可测的工作空间、限位、急停、喷嘴剂量、夹具与废液事实卡。这些是 B 写安全规则、A 做标定时的输入，不是一个 Python 包可以替代的东西。

## 不要现在安装的东西

- `ultralytics`、`torch`、`torchvision`、`torchaudio`：等待传统视觉基线在真实污染上稳定失败，并有 A/B 方案。
- 3D/点云/双视角包：等待已经记录的遮挡、反光、失焦或几何误差证明单视图不足。
- `PyYAML`：当前 YAML 由人读取，代码不解析；等代码确实要读配置再加入。
- `loguru`、`matplotlib`、`Pillow`、`requests`、`psutil`：当前 Mock 不导入它们；实际模块出现明确用途和测试时再加。

## 版本、升级与证据规则

1. 先在 `.venv` 中安装一个**小**依赖集，再运行与该任务卡对应的测试。
2. 测试通过后，记录 Python 版本、包版本、相机/驱动或固件版本到 Episode / 实验记录。
3. 只有当一个依赖集支撑了真实 E1 组件证据时，才为该层生成经过审查的精确版本锁定记录；不要把个人电脑的 `pip freeze` 直接当成全团队标准。
4. 添加新包的 PR 必须回答：它解决哪一个已记录失败？哪一层环境需要它？怎样测试？移除条件是什么？

环境不是“准备阶段”的附属品，而是可复现实验的一部分。对这个项目而言，最好的环境不是最大的，而是每个人都能说清它为什么存在、能做什么、不能做什么的环境。
