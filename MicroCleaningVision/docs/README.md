# 文档阅读导航：别在第一天被文件名淹没

这套文档不是为了显得“体系完整”，而是为了让三名成员对同一个系统说同一种语言。读文档时始终区分三件事：**已经有证据的事实、正在验证的假设、以后可能做的愿景**。

## 按你的角色读

| 你是谁 / 你现在要做什么 | 建议阅读顺序 | 读完后应能回答 |
|---|---|---|
| 刚加入项目的成员 | `09_团队入门指南.md` → `10_团队任务看板.md` → `project_state.yaml` | 我今天该做哪张任务卡？做完拿什么证明？ |
| 感知与测量负责人 A | `04_接口契约说明.md` → `06_真实实验操作规程.md` → `07_实验数据与回合规范.md` | 一张图片何时能进入系统，又为什么不能直接控制设备？ |
| 控制与安全负责人 B | `04_接口契约说明.md` → `05_研发协作流程图.md` → `08_失败分类与复盘.md` | 什么情况下必须拒绝？控制器要回传什么事实？ |
| 机构与实验负责人 C | `06_真实实验操作规程.md` → `10_团队任务看板.md` → `08_失败分类与复盘.md` | 哪些物理限制必须变成可执行的安全规则？ |
| 想判断项目是否真的进步 | `01_项目现状审计.md` → `03_最小闭环路线图.md` → `系统升级报告.md` | 当前证据等级是什么？离真实闭环还差哪一个最小实验？ |

## 文档编号的用途

| 编号 | 内容 | 为什么存在 |
|---|---|---|
| 00 | 项目研发宪章 | 定义什么不能为了“先进”而牺牲。 |
| 01 | 当前状态审计 | 防止把代码、文档或一次演示误说成真实能力。 |
| 02 | 系统架构 | 看数据怎样流、谁有权限做什么。 |
| 03 | 最小闭环与路线图 | 帮团队把注意力留在距离 E3 最近的事情上。 |
| 04 | 接口契约说明 | 规定各模块交接什么，防止越权。 |
| 05 | 研发协作流程图 | 规定证据、审查、失败和人工关卡怎样流转。 |
| 06 | 真实实验操作规程 | 第一次接触硬件前的共同安全语言。 |
| 07 | 数据与 Episode 规范 | 让图片升级为可学习的 State–Action–Outcome 数据。 |
| 08 | 失败分类 | 让失败变成下一轮实验的输入，而不是被删除的尴尬。 |
| 09 | 团队入门指南 | 让三个人都能讲清完整闭环。 |
| 10 | 团队任务看板 | 把共同目标落成可验收的小任务。 |
| 11 | 旧版文件清理记录 | 说明哪些旧模块不再是当前能力，以及为何不应恢复空壳。 |
| 12 | 开发环境与依赖说明 | 说明当前该装什么、何时才允许加相机或串口依赖。 |

## 读到英文时怎么办

- **代码类名、字段名、reason code、Git 分支名保留英文。** 它们是跨代码、测试和日志的稳定标识。
- **讨论、注释、任务与实验结论优先使用中文。** 第一次出现英文时写成“中文（`EnglishName`）”。
- 遇到不懂的术语，先问它在当前闭环里承担什么输入、输出和风险；不要先去背百科定义。

如果一段文档不能回答“谁用它、何时用、用完产出什么证据”，它就还不够可用，应在评审时改写。
