# 系统升级报告 — 2026-08-12

## 1. 原系统的真实状态

原始仓库是一个 **E0 架构/代码原型**，而不是已验证的清洁机器人。它包含一个 Git 仓库、一份详细的 README 和中文规划文档、OpenCV/YOLO/相机源码尝试、一份通用的 YOLO 权重文件，以及带类型的遗留对象。但未发现任何原始图像、数据集、标注、标定产物、固件、BOM、原理图、真实执行回执、非空实验日志或清洁前后记录。

原始的完整测试发现在当前捆绑环境中无法运行：9 个错误源于缺失 `loguru` 和 `cv2`，遗留测试中还存在进一步的静态 API 不匹配。仅语法编译通过并不构成功能性证据。

**当前物理证据等级仍为 E0。** 本次升级建立了一条 E1 **模拟契约** 基线；它不得被描述为真实相机、STM32、泵、标定或清洁验证。

## 2. 原架构的十个最大问题

1. 直接从规划调用移动/喷雾，没有独立的安全治理器。
2. 遗留入口点在没有任何物理证据的情况下默认进入自动运行。
3. Planner、coordinate、spray、STM32/protocol、calibration 和 reconstruction 中存在关键的 `pass` 桩。
4. `Frame`/检测数据并不是带有不确定性和标定有效性的任务级 StateEstimate。
5. 不存在结构化的 ActionRequest/SafetyDecision 边界。
6. 不存在实际值的 ExecutionReceipt。
7. “Return detection” 并不是一个已定义的验证指标或路径。
8. 不存在 State–Action–Outcome 的 Episode 或 FailureRecord。
9. 在测量单一视图基线之前就突出了双视图/3D/YOLO。
10. 没有研究证据档案支撑文档中所述的能力声明。

## 4. 新架构

```text
Observation -> StateEstimate -> ActionRequest (proposal)
-> SafetyDecision (ALLOW / DENY / HUMAN)
-> deterministic controller -> ExecutionReceipt
-> post Observation -> VerificationResult -> Episode / FailureRecord
```

数据流可通过 task/action/state ID 追溯；控制权限终结于安全治理器。控制器是唯一被允许实现未来物理原语的执行者，且它必须收到一个已绑定、未过期的批准。当前控制器是模拟的，从不打开端口或设备。

研发协作流程图见 `docs/05_研发协作流程图.md`。它将证据审计、架构、感知、安全、数据、集成、红队批评与文档彼此分离。Agent 仅支持工程/研究工作流；真实硬件与战略决策由人工关卡（Human Gate）掌控。

## 7. 对抗性审查

独立审查位于 `docs/reviews/红队审查_V1.md`。它发现了遗留直接控制隐患、可变的候选限位、未绑定的批准、合成模拟“成功”风险、缺失的真实证据、测试环境缺口以及不完整的证据保存。高优先级软件安全问题已修复并回归测试；物理风险仍是显式阻塞项。

## 迁移报告

本次升级先隔离遗留源码，再根据重复/空壳审计将其清理。Git 历史是恢复路径；当前源码树只保留经过验证的 Mock MCL 与科研资产。后续迁移仅在组件证据支持时才添加薄顶相机/OpenCV/控制器适配器。这避免了占位文件夹伪装成平台能力，同时不影响从正确的物理证据起步。
