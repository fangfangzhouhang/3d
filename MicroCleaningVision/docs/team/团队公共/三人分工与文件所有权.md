# 三人分工与文件所有权

## 1. 分工不是把流程切成三段后互相等待

三个人共同理解完整闭环，但分别对三种最终成果负责：

| 成员 | 一句话职责 | 最终交付 |
|---|---|---|
| A 数据与模型 | 给系统准备可信的“经验” | 可追溯数据集、人工标注、未来训练模型 |
| B 视觉识别与测量 | 给系统制造能量化污渍的“眼睛” | mask、面积、中心、误差、前后变化 |
| C 目标规划与控制仿真 | 给系统制造把测量变成动作的“手和路线” | 目标点、路线、坐标变换、FakeSTM32、回放回执 |

完整关系：

```text
A 数据/模型 → B 视觉测量 → C 目标与控制 → Episode
      ↑              ↑                 │
      └── 数据失败 ──┴── 算法失败 ─────┘
```

## 2. 顶层目录所有权

| 所有者 | 独占业务目录 | 独占测试目录 |
|---|---|---|
| A | `microcleaning/data_learning/` | `test/data_learning/` |
| B | `microcleaning/vision/` | `test/vision/` |
| C | `microcleaning/control_system/` | `test/control_system/` |

规则是“一个目录一个最终负责人”，不是“其他人永远不能看”。所有人可以阅读和运行；只有负责人直接修改。发现问题时，在Issue、PR评论或任务卡中交回负责人修复。

## 3. 共享文件

以下文件不属于任何个人随意修改：

- `microcleaning/contracts.py`：A/B/C传递的数据格式；
- `microcleaning/ports.py`：未来相机和控制器接口；
- `AGENTS.md`：全项目共同规则；
- `project_state.yaml`：当前事实；
- `README.md`、`docs/README.md`：总导航。

共享接口变更必须单独提交，写清：为什么改、谁受影响、旧数据怎样迁移、增加什么失败测试。至少由两个下游/上游成员确认。

## 5. 怎样并行而不互相卡住

### A没有准备好真实图片时

- B用程序生成的彩色斑块开发HSV和面积计算；
- C用程序生成的黑白mask开发目标点和路线。

### B没有完成分割时

- C使用固定圆形、矩形、不规则mask；
- C只验证“给定mask以后怎样规划”，不假装B已经完成。

### C没有完成控制仿真时

- A继续采集和标注；
- B继续比较算法和人工标注；
- 不需要停止数据与视觉实验。

这叫契约样例（fixture，符合正式输入格式的测试数据）。它用于解除等待，不用于冒充真实证据。

## 6. 任务量怎样平衡

不按代码行数或任务条数平均。每个任务结束时记录“专注时段”，一个时段约45～60分钟。两轮后按真实记录调整。

每轮每人都有：

1. 一个核心任务；
2. 一个扩展任务；
3. 一个不依赖上游的备用任务；
4. 一次真实接口集成；
5. 一个可检查的交付物。

AI生成代码多，不代表人类任务轻松。人工拍摄、标注和判断实验是否可信，应计入与编程同等重要的工作量。

## 7. 文件交接合同

### A交给B

```text
图片相对路径
image_id / sample_id / capture_session
设备和采集条件
人工标注或 label_status
图片质量与失败说明
```

### B交给C

```text
mask_ref
area_px
centroid_px
confidence / uncertainty
是否有目标
失败原因
```

### C返回团队

```text
目标点和路线预览
动作申请
模拟/真实回执
执行失败原因
Episode
```

## 8. 不允许的协作方式

- C复制B的算法到自己的目录；
- B为了让流程通过而修改A的质量阈值；
- A在没有独立测试集时宣布模型有效；
- 三个人同时修改同一接口文件；
- 一个大PR同时横跨三个业务目录；
- 等到三个人“各自100%完成”后才第一次集成。

## 9. Context保持一致的最小办法

每个小周期结束，三人各做一次真实操作：

- A运行B的最小演示，确认自己的数据怎样被使用；
- B运行C的路线或回放，确认自己的测量怎样变成动作；
- C打开A的数据清单，确认输入是否可追溯；
- 三个人都能用大白话复述完整链路和当前未验证内容。

不要求所有人精通别人的算法，只要求没人误解自己在整条系统中的作用。
