3. [团队入门指南](team/团队入门指南.md)：用大白话理解整条数据流。

5. [团队任务看板](team/团队任务看板.md)：本轮核心、扩展和备用任务。

## 当前目录地图

```text
MicroCleaningVision/
├── AGENTS.md                    # 全员共同上下文
├── project_state.yaml           # 唯一的当前事实表
├── microcleaning/
│   ├── contracts.py             # 共享数据合同，三人评审后才能改
│   ├── ports.py                 # 未来相机/控制器必须遵守的接口
│   ├── data_learning/           # A：数据、成像质量、未来训练
│   ├── vision/                  # B：识别、测量、状态、复检
│   └── control_system/          # C：目标、动作、仿真、未来串口
├── test/
│   ├── data_learning/           # A 的测试
│   ├── vision/                  # B 的测试
│   └── control_system/          # C 的测试
├── docs/
│   ├── architecture/            # 当前架构和长期阶段规划
│   ├── team/                    # 新人入门、分工、任务、Git、术语
│   ├── research/                # 证据、数据、失败和实验规范
│   ├── future_hardware/         # 未来硬件阶段，当前只读
│   └── archive/                 # 旧文档和历史审查，不代表当前能力
└── legacy/                      # 早期代码，仅供选择性参考
```

## 文档可信度规则

- `project_state.yaml` 写当前事实。
- `team/团队任务看板.md` 写当前行动。
- `architecture/长期分阶段研发规划.md` 写条件式路线，不是进度事实。
- `archive/` 和 `legacy/` 只说明历史，不参与当前运行。
- 代码文件存在不等于功能完成，测试通过也不等于真实硬件完成。

## 推荐阅读顺序

### 第一天

共同上下文 → 当前事实 → 团队入门 → 术语词典前四章 → 自己的任务手册。

### 第一次写代码前

文件所有权 → Git 教程 → 当前任务卡 → 对应测试文件。

### 第一次集成前

系统架构 → 接口契约 → 另外两人的“输入/输出”章节 → 软件回放测试。

### 提出 YOLO、双视角或 3D 前

长期规划中的“复杂度升级关卡” → 失败分类 → 预先写明 A/B 对照和删除条件。
