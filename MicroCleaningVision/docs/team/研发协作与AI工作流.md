# 研发协作与 AI 工作流

## 1. AI在项目中的正确位置

AI是加速器，不是项目真相来源。它适合写程序草案、测试、解释错误和审查接口；真实成员负责目标、数据、硬件、实验判断和最终接受。

```text
人定义问题和验收
→ AI解释并提出最小实现
→ 文件所有者修改/确认
→ 测试和真实数据
→ 独立审查
→ 人决定接受或退回
```

## 2. 每次让AI改代码前必须提供

```text
我的成员角色：A/B/C
任务编号：
允许修改的目录：
禁止修改的共享/他人目录：
输入样例：
预期输出：
失败情况：
验收测试：
当前真实证据：
```

如果没有说清任务，AI先解释方案，不直接改代码。所有代码变更仍须先由团队成员批准。

## 3. 推荐提示词

```text
请先阅读 AGENTS.md、project_state.yaml、docs/README.md 和我的任务手册。
我是成员B，本次任务是 B-P1-01。只允许修改 microcleaning/vision 和 test/vision。
先用大白话解释输入、输出、失败路径和测试；给出修改清单，等我批准后再实施。
实现只使用当前依赖，不增加模型或硬件。完成后运行自己的测试和全回归，区分合成、真实像素和硬件证据。
```

## 4. AI可以大量代劳的任务

- Python脚手架和参数校验；
- 单元测试和合成样例；
- 数据清单检查、标注格式转换；
- HSV、面积、目标点和简单路线代码草案；
- FakeSTM32和异常场景；
- 报错定位、代码审查和文档初稿。

## 5. AI不能替代的任务

- 拍摄真实图片、固定设备和确认样本状态；
- 给污渍边界提供最终人工真值；
- 确认机械工作空间和STM32协议；
- 判断一次真实实验是否安全；
- 把Mock或代码运行包装成硬件成功；
- 在没有批准时修改跨成员目录。

## 6. Multi-Agent怎样使用

当前Multi-Agent只用于研发，不进入产品运行时：

```text
实现Agent：只完成任务卡
审查Agent：只攻击接口、测试、证据和过度工程
真实成员：比较证据并决定是否接受
```

一个Agent不能自己提出、批准、实现并宣布成功。也不要为了“多Agent”让很多AI进行没有产出的讨论。

## 7. 并行开发和AI样例

- A没有真实图片时，B让AI生成合成色块测试；
- B没有mask时，C让AI生成合成mask；
- STM32协议没有时，C让AI生成明确标记为SIM_ONLY的FakeSTM32；
- 真实上游到位后必须替换样例再集成，不能长期停在合成数据。

## 8. 每次AI交付后的人类复检

```text
[ ] 文件是否属于当前负责人
[ ] 是否偷偷增加依赖或未来模块
[ ] 程序是否真正处理输入，而不是硬编码答案
[ ] 正常、边界和失败测试是否存在
[ ] 文档是否夸大证据等级
[ ] 运行命令是否真的执行过
[ ] 下游是否能消费输出
[ ] 是否保留失败样本和未验证内容
```

## 9. 项目Skill

`.codex/skills/visual-closed-loop-task/SKILL.md` 是项目内重复使用的AI开工流程。它要求先读共同上下文、遵守目录所有权、运行测试并区分证据。Skill是方法，不是一个自动工作的Agent。
