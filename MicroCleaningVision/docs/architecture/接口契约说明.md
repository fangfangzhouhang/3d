# 接口契约说明 v0.1（`mcl-v0.1`）

## 先用一句人话理解它

接口契约就像实验室里的“交接单”。相机不能拿着图直接让泵喷水；它只能把**看到了什么**交给下一环。每一环接单、判断、执行后再签字回传。这样出了问题才能知道：是看错了、算错了、审批错了，还是设备根本没有按要求动。

这些对象是结构化的 Python 数据类。序列化后不能丢掉 ID、坐标单位、版本号或拒绝原因。真实硬件适配器只能遵守它们，不能私自删字段、补默认值或绕过步骤。

| 代码对象 | 中文角色 | 谁交给谁 | 它回答的关键问题 |
|---|---|---|---|
| `Observation` | 观测记录 | 成像 → 状态估计 | “这一刻相机实际拍到了什么？图像够不够清楚？” |
| `StateEstimate` | 状态判断 | 状态估计 → 决策 / 安全 | “污渍在什么坐标？这个坐标可靠吗？设备现在准备好了吗？” |
| `ActionRequest` | 动作申请单 | 决策 → 安全 | “我建议做一次什么样、范围多大的动作？”它只是申请，不是命令。 |
| `SafetyDecision` | 安全审批单 | 安全 → 控制器 | “允许、拒绝，还是必须由人判断？”允许时才会带短时有效的批准令牌。 |
| `ExecutionReceipt` | 执行回执 | 控制器 → 验证 | “设备实际上做了什么，是否超时、限位、断连或失败？” |
| `VerificationResult` | 结果复查单 | 验证 → 路由 | “污渍是否减少、是否可能损伤、现在应停止、重试还是叫人？” |
| `Episode` / `FailureRecord` | 完整实验档案 / 失败记录 | 全流程 → 数据资产 | “这一回合从看到结果，中间究竟发生了什么？” |

## 读代码时的三个常见误解

1. **图像不是状态。** 一张看起来有污渍的图，如果没有标定、图像质量、坐标系和不确定度，就不能用来定位喷头。
2. **动作申请不是执行命令。** `ActionRequest` 中有建议参数，不代表任何硬件已经收到指令。
3. **成功日志不是实验成功。** 只有 `ExecutionReceipt` 证明设备确实执行，再由 `VerificationResult` 的真实后观测证明效果，才谈得上一次结果。

## 真实控制器不可妥协的底线

- 不接受任何自然语言命令，也不接受“模型说可以”的口头授权。
- 执行前验证动作 ID、批准令牌、有效期、设备状态、坐标系和单位是否一一对应。
- 在确定性下层再次强制工作空间和剂量限制；上层漏检不能变成物理风险。
- 即使失败也必须给出回执；如果不知道是否执行过，就进入人工处理或安全停止。
- 一条 Episode 中不得静默更换标定、模型、规则或硬件版本。

> 记忆口诀：**看见不等于知道，申请不等于允许，发令不等于执行，执行不等于成功。**

## v0.1为什么同时保留像素和毫米

第一版真实图片只能测到 `centroid_px` 和 `uncertainty_px`。这相当于知道污渍在图片第几列、第几行，却还不知道喷头应该移动多少毫米。

因此 `StateEstimate` 现在明确区分：

- `target_centroid_px` / `uncertainty_px`：B从图片得到的像素测量；
- `target_centroid_mm` / `uncertainty_mm`：只有经过有效标定后才允许出现；
- `coordinate_frame=image_px`：只能做路线预览，不能执行物理动作；
- `coordinate_frame=work_mm`：仍需通过Safety Governor，才可能交给控制器。

Demo的`simulation-normalized-v0`只把图片归一化到虚拟100×100工作区，用于FakeSerial。它不是相机到真实工作台的标定文件。
