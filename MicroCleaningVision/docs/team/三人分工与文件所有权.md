# 三人分工与文件所有权

## 为什么要“理解全局，修改局部”

三个人完全互不看对方，会在接口处集成失败；三个人同时改一个文件，又会产生冲突和责任模糊。解决办法是：所有人共同理解一条数据流，但每个业务文件只有一个所有者。

```text
A：Observation → B：Measurement/State/Verification → C：Action/Safety/FakeSerial/Episode
```

## 文件所有权

| 所有者 | 独占业务文件 | 自己维护的测试 |
|---|---|---|
| A 成像 | `perception/image_quality.py`、`adapters/replay_camera.py` | `test_member_a_imaging.py` |
| B 测量复检 | `perception/contamination.py`、`state/estimator.py`、`verification/area_change.py` | `test_member_b_measurement.py` |
| C 闭环接口 | `decision/fixed_rule.py`、`safety/governor.py`、`execution/fake_serial.py`、`data/episode_store.py`、`app/replay_mcl.py` | `test_member_c_workflow.py` |

目录中的 `__init__.py` 只做包说明，不承载业务逻辑。

## 共享文件

`contracts.py`、`adapters/ports.py`、`AGENTS.md`、`project_state.yaml` 是共享文件。由 C 负责日常维护，但任何接口字段或项目事实变化都必须经过另外两人评审。A/B 不直接编辑，而是在 PR 写“接口变更提案”。

## 每个人都必须知道的全局问题

- Image 为什么不等于 State：图片是原始证据，State 是带不确定度的任务判断。
- ACK 为什么不等于成功：ACK 只说明控制端回应，清洗效果必须由后图复检。
- 为什么坏图要停止：错误观测继续流动，会变成错误坐标和错误动作。
- 为什么 FakeSerial 不是 STM32：它只验证上位机接口和异常路由。
- 为什么不马上用 YOLO：当前没有证明简单阈值在固定场景下失败。

## Git 协作

- A：`feat/a-imaging-*`
- B：`feat/b-measurement-*`
- C：`feat/c-replay-*`
- 一张任务卡一个分支、一个主要模块、一个 PR。
- PR 必须由下游消费者评审：A 的 PR 由 B 审；B 的 PR 由 C 审；C 的 PR 由 A/B 至少一人审。
- 禁止一个 PR 同时重写 A/B/C 三方文件。

## 交接格式

每次交付写清：输入示例、输出示例、失败情况、测试命令、接口是否变化、下游下一步需要什么。
