# 旧版文件清理记录 — 2026-08-12

## 为什么清理

升级前的目录把“未来可能会有的平台”与“现在真正能工作的项目”混在了一起。规划、STM32 通信、标定、双目/3D、模型训练和工具壳中大约有 190 个 `pass` 占位；旧文档却容易让人把这些占位误认为能力。继续保留它们，会诱导后来的人把真实硬件接到未完成、也未经安全审查的路径上。

因此它们被从可运行源码中移除，而不是留作“以后再填”的空文件。若未来某个想法被真实失败证据支持，可以从仓库根目录的 Git 历史中找回对应参考；找回不等于恢复为可运行模块。

## 清理了什么，以及何时才允许回来

| 清理项 | 为什么不能保留 | 未来重新引入的门槛 |
|---|---|---|
| `planning/`、`communication/` | 核心逻辑是空壳，且旧组合根绕过了安全审批 | 已记录真实协议、物理限位、急停/联锁和人工关卡后，才写新的薄适配器。 |
| `reconstruction/`、双目/光照/标定空壳 | 无单模块证据，且不是 P1 所需 | 只有固定顶视图确实失败、且对照实验表明它有用时才加入。 |
| YOLO / 模型 / 训练空壳与通用权重 | 没有项目数据集、评估、配置路径或有效性证据 | 先完成传统视觉基线，再以预登记 A/B 计划证明模型必要。 |
| 旧 config/logger/types/utils | 只服务已删除的不完整流水线，还依赖额外环境 | 以 `microcleaning/contracts.py` 作为新的 P1 接口边界。 |
| 旧测试与环境脚本 | 当前环境无法通过，且断言与接口不一致 | `test/mcl/` 是当前无依赖回归基线。 |
| 重复说明、旧 README、IDE 元数据、空日志 | 重复、夸大能力、仅是本地状态或没有证据 | 以 `docs/00`–`docs/10` 与 `系统升级报告.md` 为准。 |

## 明确保留的内容

- `microcleaning/`、`test/mcl/`、`docs/`、`skills/`、`project_state.yaml`、`系统升级报告.md`。
- Git 历史：它是旧原型的“考古档案”，不能被当作当前功能。

## 清理后的现实含义

当前仓库**刻意没有**真实硬件适配器。这不是功能缺失被掩盖，而是一条安全边界：未来相机或 STM32 接入必须是薄、小、可测试的适配器，只接收并输出既有契约中的结构化对象。
